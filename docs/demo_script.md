# Phase 2 judge demo — approximately four minutes

Start locally with `./start.sh`, select Rina and reset the demo. Today is a simulated October date, not a live wallet balance.

## Product story

Scammers can persuade customers to authorize payments themselves. Thamun offers a pre-authorization moment to pause, understand and decide. This prototype uses synthetic customers and simulated payments; it does not control any real wallet OTP.

## Payment → explanation → evidence → evaluation → impact

1. Run the regular bill scenario. Show SILENT and enter a made-up four-digit demo code, never a real OTP.
2. Run the food scenario. Explain the supported coaching NUDGE; do not call it a scam.
3. Run the refund scenario and choose the refund purpose. Inspect history, unavailable matching incoming funds and the supported pause reasons. Cancel or acknowledge before continuing.
4. Run a reported-recipient scenario. Explain that seeded reports are synthetic and community allegations remain unverified; reports are not confirmed guilt.
5. Click Bangladesh Real Evidence below Why it decided. Filter case studies; open a case; distinguish broader MFS credential fraud from APP relevance. Inspect original sources and the full report. Point out unverified PDF/police entries without inventing numbers.
6. Open AI / ML Analysis. Explain calculated synthetic temporal baselines/ablations and purpose assumptions. Public evidence does not establish model performance.
7. Open Prototype Impact. Show actual session pause/cancellation events; cancelled value is not proven fraud loss avoided.
8. Return to bills, review, savings goals and Ask; switch customer/language to show preserved bilingual coaching.

## Honest judge answers

- Real-world accuracy? Unknown; only simulator evaluation exists.
- Does a new number mean fraud? No, it is contextual information.
- Does this stop all OTP scams? No; credential theft and payments outside the prototype are out of scope.
- Can reporting be abused? Yes. Deduplication/confidence/limits are prototype safeguards; provider-linked identities, moderation and appeal are future work.
- Is persistence production ready? Reports, decisions and demo snapshots persist; financial atomicity and multi-worker coordination need further implementation.
- Why a separate evidence page? To distinguish checked Bangladesh problem evidence from synthetic ML results.
- What do you miss? Manipulated payments resembling normal known-recipient behavior can be missed.
- How does it integrate? A proposed provider-authorized pre-authorization API boundary; no live integration exists in this archive.
